# Diagnosing a macOS Electron helper startup crash

The September 20 diagnostic established the cause of one **task-owned diagnostic app** crash. Its launch record changed the main app's `CFBundleName` from `OpenSaddle` to `OpenSaddle Resume Diagnostic` while leaving the bundled helper app names unchanged. Three seconds after launch, stderr reported `electron_main_delegate_mac.mm:66: Unable to find helper app`; the attached crash report recorded `EXC_BREAKPOINT (SIGTRAP)` for that process at the same time. The matching launch and stderr establish the historical diagnostic failure more directly than the unsymbolicated crash stack alone.

An isolated APFS clone reproduced the boundary with a minimal Electron app that opened a hidden `BrowserWindow`, loaded local `data:` HTML, and waited for `did-finish-load`. Changing **only** the main `CFBundleIdentifier` loaded the renderer. Changing **only** the main `CFBundleName` caused the same helper fatal and SIGTRAP before the renderer loaded. Changing both also failed; restoring the original name and identifier loaded the renderer. Each clone passed strict ad-hoc code-signature verification. This is a diagnosis of the diagnostic bundle, not a production code fix or a qualification of the user's installed OpenSaddle app. [Sanitized receipt](receipts/electron-diagnostic-helper-startup-20260920.json)

For another controlled startup probe, preserve the main app's bundle name and identifier together with the helper bundle names and identifiers. If a diagnostic variant must rename the app, update the helper metadata consistently and re-sign the clone. Launch only the task-owned clone with a private `HOME`, an explicit private `--user-data-dir`, private state and temporary directories, and no provider, network task, or sidecar. A private `HOME` alone is insufficient evidence that Chromium will avoid the standard profile. Capture the exact launch command, stderr, exit signal, and a renderer `did-finish-load` marker; correlate the process and time with the crash report before assigning cause. Do not launch the original installed app as part of this probe.

The original private package's ASAR header hash matched its plist, and its embedded ASAR integrity-validation fuse was disabled. A separate minimal startup probe with a deliberately stale ASAR header still exited normally. That experiment ruled out the stale-header hypothesis for this package configuration; it did not qualify every Electron packaging configuration. The original installed app's startup and any earlier standard-profile writes remain separate, unqualified questions.
